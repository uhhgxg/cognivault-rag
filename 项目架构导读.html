🎯一句话概括

先建立最粗的全局印象，再往下看细节。

RAGent 是一个企业级 RAG 知识库：把文档喂进去，用户用自然语言提问，系统理解意图 → 检索相关知识 → 让大模型基于知识回答，还能记住对话、调用外部工具。
📚
通俗类比

你可以把 RAGent 理解为一个"会查资料的 AI 图书管理员"：传统大模型像一个"只凭脑子答"的人，容易胡说；RAGent 给它配了一座图书馆，每次回答前先去翻相关资料，再据实回答，还标注引用来源。而 RAG（Retrieval-Augmented Generation）就是"检索增强生成"——先检索、再生成。

🏢业务背景（先懂业务再看代码）

为什么要有这个项目？它解决谁的什么问题？

💡
核心痛点：传统企业知识库只会"关键词搬运"——搜"年假怎么休"只能命中含"年假"两字的文档，换个问法"带薪休假"就找不到了。用户要的是被理解，不是被匹配。

用户是谁：需要管理企业文档、并对文档内容进行智能问答的团队（内部知识库场景）。

核心业务场景：

📤 文档摄入
上传 PDF/Word/Excel/PPT/Markdown 等多种格式文档，系统自动拆分、贴标签、向量化、存进知识库。
💬 智能问答
用户自然语言提问，系统理解意图，混合检索相关知识，让 LLM 基于资料回答并标注引用。
🧠 对话记忆
支持多轮对话，记住上下文；还能跨会话记住关于用户的长期事实（LTM）。
🔌 工具增强
遇到知识库答不了的，Agent 可调用外部工具（MCP/内置工具）来补全答案。
🗄 会话隔离
每个对话一个独立知识库，互不串味，适合多项目/多团队场景。
📊 可观测评估
全链路 Trace 追踪 + Ragas 评估质量，知道检索/生成到底好不好。

⚙️技术栈速览

每个技术都附一句大白话，别被名词吓到。

维度技术选型大白话解释
语言Python 3.10+项目要求 ≥3.10，实际用 3.12 开发
Web 框架FastAPI + Uvicorn提供 HTTP 接口和 WebSocket 实时推送，Uvicorn 是跑它的服务器
工作流引擎LangGraph + LangChain把"提问→检索→生成"画成一张状态图，节点间可跳转，这就是 Agent 的"大脑流程图"
LLM 接入自研工厂模式一套接口接多家大模型（OpenAI/Azure/DeepSeek/Ollama），换模型只改配置
Embedding工厂模式把文字转成向量（一串数字），让机器能比较"意思相近"
向量库ChromaDB存向量并按相似度检索的专用数据库，本地 SQLite 持久化
稀疏检索自研 BM25传统关键词匹配算法，弥补向量检索对"专有名词/代号"的弱点
关系库PostgreSQL (asyncpg)存对话元数据、归档消息、文件信息、长期记忆、Checkpoint
MCP 协议官方 MCP SDK让外部 AI 客户端（如 Claude）能通过标准协议调用本系统的知识库能力
前端Vue 3 + Vite + Element Plus单页应用，支持对话、上传、Trace 面板
DashboardStreamlit给运维用的可视化面板，看摄取记录、查询 Trace、评估结果
评估Ragas + 自定义 Evaluator给 RAG 系统打分的框架，看回答准不准、检索全不全
文档解析markitdown + docx/openpyxl/pptx把各种格式文档统一转成 Markdown 再处理
中文分词结巴分词 jieba把中文句子切成词，给关键词检索用

🌊三大主线数据流

把项目拆成三条线来看，每条线都别想太复杂，跟着箭头走。

主线一：文档摄取（Ingestion）——把书买回来上架

📥
类比

主线二：混合检索（Hybrid Search）——双管齐下找资料

🔍
类比

找一本书时，向量检索像"按意思找"（你说"带薪休假"能找到"年假"），BM25 像"按字面找"（精确命中关键词）。两个各有短板，所以两条路都走，再用 RRF 把结果揉到一起排序，最后用 Rerank 精排——这是 RAG 检索质量的核心秘诀。

⭐
铁律：上层可以调下层，下层不能调上层。比如工作流层（L2）可以调检索引擎（L3），但检索引擎绝不能反过来启动一个工作流。这样依赖方向永远是单向的，不会绕成死结。
层餐厅类比本项目对应依赖方向
对外接口层服务员接单、传菜ragent_backend/app.py、mcp_server/→ 调下层
业务编排层厨师长按流程派活workflow.py、pipeline.py→ 调下层
核心引擎层切菜、炒菜、调味的手艺core/query_engine、ingestion/chunking→ 调下层
基础设施层买菜的外包、水电煤气libs/（LLM/Embedding/向量库工厂）被大家调

场景：用户在前端问"去年的销售数据在哪份报告里？"

第1跳：前端发请求
📁 frontend/src/App.vue → POST /chat，建立 WebSocket 收流式回复。
第2跳：FastAPI 接单
📁 src/ragent_backend/app.py，校验会话、加载历史、启动 RAGWorkflow.astream()。
第3跳：意图识别
📁 src/ragent_backend/intent.py 的 detect_intent，判断走 RAG / 澄清 / 工具三分支。⭐ 这是分叉点。
第4跳：混合检索
📁 src/mcp_server/tools/query_knowledge_hub.py → src/core/query_engine/hybrid_search.py，并行 Dense+Sparse→RRF→Rerank。
第5跳：LLM 生成
📁 workflow.py 的 _generate_node，把知识块+问题塞进 Prompt，流式产出回答。
第6跳：记忆压缩

🔀工作流三分支：意图路由的关键决策

intent 节点是整个工作流的核心分叉口，搞懂它就懂了"为什么会走不同路"。

分支触发条件走向通俗解释
clarify 澄清问题模糊/信息不足反问用户补充用户问"那个报告"，系统反问"哪份报告？什么时间？"
rag 检索明确查知识库retrieve→generate正常查资料并回答，是主路径
tool 工具需调用外部能力tool_subgraph知识库答不了，Agent 调 MCP/内置工具补全（如查天气、算数）
💡
理解技巧：LangGraph 的"分支"其实就是条件边（conditional edge）——intent 节点输出一个路由 key，图根据 key 决定下一跳去哪。你搜 add_conditional_edges 就能看到这个分叉逻辑。

🧭新手生存指南

少踩坑就是快。这几条比看懂任何代码都重要。

⭐
最重要：先读 config/settings.yaml 再读任何代码。这个项目是"配置驱动"的——LLM 用哪家、检索用啥参数、摄取开关哪些，全在配置里。很多"看起来像 Bug"的问题其实是配置没改对。
⚠️
第二重要：会话级隔离是核心设计。每个对话的向量集合叫 conv_{conversation_id}，别以为所有文档在一个大池子里——你换对话就换知识库了。调试时若"刚上传的文档查不到"，先确认是不是查错了 collection。
💡
第三重要：工厂模式到处都是。LLM、Embedding、向量库、Reranker、Splitter 全是 xxx_factory.py。改某个能力的实现，找对应工厂的 create()，别去业务代码里硬改。
💡
第四：Trace 是你的好朋友。logs/traces.jsonl 记录了每次摄取/查询的完整阶段耗时和元数据，出问题先看 Trace，比看代码快十倍。Dashboard（Streamlit）还能可视化。
⚠️
第五：入口不止一个。main.py 只是配置校验占位；真正的后端入口是 src/ragent_backend/app.py（FastAPI），MCP 入口是 src/mcp_server/server.py。别被 main.py 误导。
