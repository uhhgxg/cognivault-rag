记忆与上下文处理详解

RAGent 如何记住对话、压缩上下文、跨会话记住你——三层记忆 + 长期记忆的完整设计

🗺️先看全貌：四层记忆体系

这个项目的记忆不是简单的"消息列表"，而是精心设计的四层结构，各司其职。

🔥第一层：热记忆——模型的"工作内存"

这是 LLM 每次回答时真正能看到的记忆，存在 LangGraph 的状态里。

热记忆 messages + summary
位置：RAGState（LangGraph 状态），由 Checkpointer 持久化到 PostgreSQL
  • messages：对话消息列表，用 LangGraph 的 Annotated[list, add_messages] 管理——支持追加新消息，也支持 RemoveMessage 删除旧消息
  • summary：滚动摘要字符串——旧消息被压缩后，精华内容存在这里

1核心机制：滑动窗口压缩

消息不能无限堆下去（LLM 上下文有限 + 越来越贵），所以项目用了滑动窗口 + 滚动摘要的策略：

窗口上限
max_messages = 20
保留最近
keep_recent = 4
摘要上限
summary_max_length = 500字

2压缩过程（memory_manage 节点做的事）

1
检查消息数是否超过 max_messages(20)，没超就啥也不做直接返回。
2
超过了就保留最近 keep_recent(4) 条，其余的要被"裁掉"。
3
把裁掉的消息 + 旧 summary 一起喂给 LLM，让它重写一个新摘要（保留专有名词、结论、用户偏好，只压缩冗余）。
4
生成 RemoveMessage(id=xxx) 操作列表——LangGraph 的 add_messages 注解遇到 RemoveMessage 会自动删对应消息。
5
返回 {messages: delete_ops, summary: new_summary, _to_archive: archived_data}。
💡
关键设计：messages 字段用了 Annotated[List[AnyMessage], add_messages]，这是 LangGraph 的"消息归约器"——返回普通消息就是追加，返回 RemoveMessage 就是删除。状态更新不是全量覆盖，而是"增量操作"，这让多节点并发写消息也不会互相覆盖。

3降级策略（LLM 挂了也不怕）

如果 LLM 重写摘要失败，会走 _fallback_summary：简单拼接旧摘要 + 最近4条归档消息的前120字。虽然质量差点，但系统不会崩。

📁 关键代码：src/ragent_backend/memory_manager.py → RollingMemoryManager

🧊第二层：冷记忆——完整历史归档

热记忆会被压缩，但用户想看完整对话怎么办？答案是——分开存。

冷记忆 conversation_archive 表
位置：PostgreSQL，由 ConversationArchiveStore 管理
  • 存的是完整历史：所有消息一条不落，给前端展示"对话记录"用
  • 异步写入：用 asyncio.create_task 后台写库，不阻塞用户拿到回答
  • 按 turn 标记：每条消息都带 turn_id，支持回滚到任意一轮
  • 不给模型看：LLM 回答时不会加载这些，只给用户界面展示用
📋
通俗类比

热记忆就像你电脑上的"内存条"——快、但容量有限，只放当前在用的东西。冷记忆就像"硬盘"——容量大、慢点没关系，存所有历史文件。你写文档时只看内存里的内容，但完整文件都在硬盘上存着。

归档节点（archive 节点）做的事

1
拿 _to_archive（被压缩的旧消息，可能为空）。
2
从当前 messages 取最后2条（本轮的用户问题 + 助手回答）。
3
合并后用 asyncio.create_task 异步写入 conversation_archive 表，带 turn_id。
4
顺便触发 LTM 提取（也是异步），从本轮 Q&A 里提炼用户事实。
⭐
重点：archive 节点总是运行（工作流的最后一站），无论有没有压缩，本轮新消息都会被归档。这样冷记忆永远是完整的，热记忆可以放心压缩。

📁 关键代码：src/ragent_backend/store.py → ConversationArchiveStore

🧠第三层：长期记忆 LTM——"我记得你"

跨会话的用户画像记忆。你开新对话，它还能想起你是谁、喜欢什么。

长期记忆 long_term_memories 表
位置：PostgreSQL，由 LTMStore 管理
  • 存的是结构化事实：比如"用户是金融风控工程师，用 Python"、"用户偏好简洁的技术回答"
  • 自动提取：每轮对话结束后，让 LLM 从 Q&A 里提炼 0~3 条用户事实
  • 自动召回：新对话开始时（session 节点），根据当前 query 召回最相关的 3 条注入 state
  • 按用户隔离：每个 user_id 有自己的记忆池，不会串

召回排序算法（不用向量，用轻量规则）

LTM 召回没有用向量检索，而是一个很轻量的打分公式：

score = 关键词命中数 × 10    # query 里的词在事实里出现几次
      + max(0, 24 - 年龄小时数)  # 时间衰减，24小时内的记忆加权重
      + 访问次数 × 2            # 被召回过越多越重要
🎯
通俗类比

长期记忆就像你的"人脉本"——每认识一个人，记下几条关于他的关键信息（职业、喜好、禁忌）。下次见面时，先翻翻人脉本找几条最相关的揣在心里，聊天时就显得"你还记得啊"，很贴心。

💡
设计巧思：LTM 提取是异步在 archive 节点做的，不增加用户等待时间；召回只在 session 节点做一次，也只取 top 3，不会让 prompt 膨胀。低开销、高收益。

📁 关键代码：src/ragent_backend/ltm_store.py → LTMStore

📚第四层：知识库记忆——RAG 的"外部大脑"

这层是 RAG 的本质：把文档变成可检索的知识，回答时拿出来当参考。

知识库记忆 ChromaDB + BM25
位置：ChromaDB（向量）+ JSON 文件（BM25索引），会话级隔离
  • 会话级隔离：每个对话一个 collection，名字是 conv_{conversation_id}
  • 双索引：向量索引（语义匹配）+ BM25 索引（关键词匹配），混合检索
  • 什么时候注入：retrieve 节点根据 query 检索出 top_k 条相关知识，拼进生成时的 prompt
  • 不算"对话记忆"：它是外部知识，不是对话历史，但对回答质量至关重要

⏪高级功能：三层时间裁剪回滚

用户说"回到上一步"时，系统能精确回滚到任意一轮。怎么做到的？

答案是 turn_id + 三层联动删除：每轮对话都生成一个唯一的 current_turn_id，标记在所有相关数据上。回滚时按 turn_id 一起删：

第1层
Checkpoint
LangGraph 状态回退
第2层
conversation_archive
归档消息删除
第3层
long_term_memories
该轮提取的LTM清除
⭐
为什么厉害：很多 RAG 系统回滚只删界面上的消息，实际上模型记忆还在（"表面忘了，心里还记得"）。这个项目是三层一起回滚——模型状态、用户可见历史、长期记忆全部清理干净，真正的"时光倒流"。

⚠️新手易踩的 5 个坑

1
"我删了消息，模型怎么还记得？"
你可能只清了前端界面或 archive 表，没清 LangGraph 的 Checkpoint。热记忆在 Checkpoint 里，模型靠它思考。
2
"为什么对话超过20条后，早期的内容模型忘了？"
因为滑动窗口压缩了——旧消息被揉进 summary 了，细节会丢失。这是正常的 trade-off（上下文长度 vs 记忆精度）。
3
"我换了个 conversation_id，文档怎么搜不到了？"
因为知识库是会话级隔离的，每个对话一个独立 collection。上传到 A 对话的文档，B 对话看不到。
4
"LTM 怎么没生效？"
LTM 是按 user_id 存的，user_id 默认是 "1"。检查你传的 user_id 对不对，而且要至少完成一轮完整对话（archive 成功）后才会有 LTM 记录。
5
"归档消息写入失败了怎么办？"
归档是异步的，失败只会打日志，不会影响用户拿到回答。去看控制台日志里的 [Archive] Failed，多半是 PostgreSQL 没连好。
